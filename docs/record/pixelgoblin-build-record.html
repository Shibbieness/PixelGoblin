"8-bit to 256-bit", honestly

You asked for characters that work at 8, 16, 32, 64, 128 and 256 "bit". Part of that is exactly right, and part of it points at something a little different, so here is the split before anything else.

What is exactly right

A character should survive being drawn tiny and being drawn large, and still be that character. That is the core of it, and it is built. The sizes 8, 16, 32, 64, 128 and 256 are the right ladder: each one doubles, and they all divide PixelGoblin's 1024-unit design space evenly, so every tier samples the same geometry with no rounding drift.

What is slightly off

"8-bit", "16-bit" and so on name console CPU generations, not sprite sizes. An NES (8-bit) drew 8×8 and 16×16 sprites; a Super Nintendo (16-bit) drew 8×8 up to 64×64. So "a 32-bit character" is not a size. It is a look: how many colours, how the shading bands, what the outline does. And 128-bit and 256-bit consoles never had a pixel-art style of their own. Their 2D art is what people now call HD pixel art.

So PixelGoblin keeps two settings, never merged

SettingValuesWhat it controls
Tier8, 16, 32, 64, 128, 256 pxResolution: which features exist at this size, shade bands, outline width, chibi head and eye bonus
Era8-bit (3 colours), 16-bit (15), 32-bit (31), HD (255)The look: palette budget, band count, outline style, dithering

A character's build bit chain uses a default era per tier (8 px → 8-bit, 16 and 32 px → 16-bit, 64 px → 32-bit, 128 and 256 px → HD). Any era can be forced at any tier, because "an 8-bit-look 64 px sprite" is a real style people want. The full spec is in docs/explanation/tier-chain.md.

Coherence compares each tier against a 256 px drawing with the same stylisation and feature set, reduced to the small grid. IoU is silhouette overlap; material is the share of shared pixels with the same material. This run measured it across all 28 goblin types at seed 0:

TierIoU averageIoU minimumMaterial averageMaterial minimum

Read it plainly. From 32 px up it is very nearly the same drawing. At 16 px it is clearly the same character. At 8 px the colours still agree, but only about three-fifths of the outline does, because in an 8×8 grid every snapped ear is a big share of the picture. An 8 px sprite is an icon of a character, not a small copy of it. Hand-made sprite chains work the same way. Legs were checked 336 times this run (every role, three seeds, 8 to 64 px), with 0 failures.

What breaks this, what fixes that, what I'd add

What breaks this now

  1. 8 px identity is modest. An average IoU of about 60% is honest, but it means two roles can collapse to near-identical 8 px icons. Fix: give every role a signature: one colour or one pixel shape reserved for it at 8 px (the chief's feather, the smith's hammer), stored as data and checked with a "no two roles share an 8 px icon" gate. After that, allow optional hand-authored 8 px overrides as data, still checked against the chain.
  2. The rider has no mount. The role exists, but a rider standing on the ground is a costume. Fix: a mount is its own rig (a beast genome: legs, neck, tail) with a saddle anchor; the rider renders at that anchor. Same tiers, same eras, same gates.
  3. Scene props have no tiers. Huts, stalls and trees are drawn straight into the canvas, so the HD village's huts are just bigger, not more detailed. Fix: move props onto the same design-space shape renderer (a "prop rig"), so a hut gains planks and windows at 128 px the way a goblin gains pupils.
  4. Adding an item means editing Python. The 24 held items, the headwear and the tops are geometry in rig.py. Fix: item shapes as data (a short list of E/R/C/T/A shapes per item in a TOML file). That also makes items moddable, and the transpiler then only has to cover the interpreter.
  5. The transpiler covers a small subset of Python. It refuses anything else loudly, which is right, but a future geometry edit in an unusual style will stop the build. Fix: keep geometry in the documented subset, or extend the emitter one construct at a time with a parity case for each.
  6. The JavaScript render, era reduction and scene are hand-ported. Gate B13 holds them to Python pixel for pixel (every rig type, 8 to 64 px, six at 128 and 256; both villages; a family), but it is still two copies. Fix: the P1 Rust core compiled to WebAssembly replaces both, and the goldens bind it.
  7. Speed. A 256 px character takes about 0.2 s in Python, and an HD village about a second. That is fine for tools and load screens, not per-frame. Fix: every sprite is a pure function of (type hash, seed, tier, era, pose), so a cache is trivially correct; then the Rust core.
  8. Era reduction can eat an identity colour. The merge is global and greedy, so at 3 colours an iris or a signature colour can merge into skin. Fix: weight identity materials the way the outline is already locked.
  9. I witnessed the golden re-bless, not you. The goblin legs, the iron ramp and the 8 px feet changed 8 goldens, and 165 new ones were added. Fix: look at the roster above, then re-bless with your name as witness: python3 tests/gate.py --bless-goldens --witness Mark --reason "reviewed roster".
  10. Coherence measures shape and material, not recognition. Fix: a two-minute human gate: shown a random 16 px goblin and its 128 px lineup, can you pick it? That belongs with the P5 usability gates.
  11. The 11 new SLM-e pieces are unvalidated. SLM-e could not be reached from this session. Fix: run validate_manifest on slme/pieces.json once, then register all 27.

What I'd add next, in order

  1. Role signatures and an 8 px uniqueness gate (fix 1 above). This is the biggest gain for the smallest tier.
  2. Expression sheets. All nine expressions already exist in the genome vocabulary; a sheet is nine renders with one field swapped. Nearly free.
  3. Faction palettes. Cloth overrides per team or clan: the same goblin in the chief's colours or a rival warren's. Nearly free.
  4. Mounts (fix 2), then prop tiers (fix 3).
  5. Side and back views. The front view is built; a walk cycle needs a side view. This one is real work: side-view geometry per feature, and a gate that the side view's colours match the front's.
  6. Tier transitions. A zoom from a 32 px crowd goblin to its 128 px portrait, using a pixel dissolve between chain tiers. The chain already guarantees features only arrive and never move.
  7. A Book of Cities NPC pipeline: name → role → subspecies → family → village slot, all deterministic, so a city's whole population regenerates from a list of names.

What I think

The split between genome and render was the right call, and your "features should translate up and down" instinct is what made it obvious. Once the character is data that never sees the tier, identity across sizes stops being a hope and becomes something you can measure, and the three-leg bug stops being something to remember and becomes something a gate refuses. The weakest tier is 8 px, and the page says so in numbers instead of hiding it.

Bugs found this session

  • Three legs on the original goblins: the template's mirror put a # in the centre column. Fixed in the template, with a legs verdict that the old template fails.
  • The first 8 px rig came out as one flat colour, lost its ears and was lanky. Top, bottom and hair moved to the 8 px rung, triangles got a snapped spine, and the chibi head and eye bonuses were added.
  • 16 px eyes merged into a bar. Eye spacing now keeps a one-pixel gap.
  • Leg counting gave false failures five different ways: hanging items, a bow across a leg, the hip row, an apron, and a lute that really does hide a leg. The fix was to split the check in two: drawn alone, the legs must be exactly two; drawn dressed, items may hide one and never add one.
  • 8 px guards had no legs at all: spear and shield covered both. Found by the new JavaScript parity run's leg report, not by eye.
  • The crowd stood in the water, and the chief appeared twice. Placement now uses feet positions, and roles come from a pool without repeats.
  • Iron rendered white, and copper's shadows clipped. The CRUCIBLE glint steps were softened, and shadow chroma lowered.
  • The transpiled JavaScript crashed: a Python variable set inside an if was invisible after it in JavaScript. Locals are now hoisted to the top of each function.
  • Gate B03 read size as pixels for every generator. For a rig it is the largest tier, and for a Warren it is tiles. It is now generator-aware.

Bugs found along the way

In your stack

Vanilla Core, composite loading. QRen Coder and PixelGoblin both name their entry module vanilla_flavor. Python caches modules by name, so the second flavor loaded silently received the first one's code. Asked for block-types, QRen answered as PixelGoblin. patches/vanilla-core-composite-fix.patch fixes it (12 lines plus a regression test). All 40 Vanilla Core tests pass with it, and the new test fails without it. A flavor's helper modules can still collide if two flavors share names like utils; the full fix is per-flavor import isolation, noted for Vanilla Core's STANDARDS.md.

In PixelGoblin, caught by its own gates

  • 5 surviving mutants on the first falsification run. One was a test that could never see a shared stream. One was a 9-slice check blind to stripes. One was a leak-guard control that two patterns both caught. Two were mutations written wrong. All five were fixed in the checks, not exempted.
  • The L-corner definition was wrong: a staircase control had "zero" corners. It was rewritten to match how pixel-perfect strokes actually work.
  • The likeness ramp learned the outline as a skin colour, which gave black relatives. It now learns from interior pixels, weighted by coverage.
  • WFC 3×3 falls back at 48×48, which the gate never tested. It was measured, the default changed, and the limit is written down.
  • The first JavaScript ↔ Python parity run passed on every case. That is a result, not a bug, and gate B13 keeps it true.

Critique, round 2 (session 2)

Round 3 is at the top, under Breaks, fixes, additions. Everything in round 2's "nearly free" list, the parts_add fix, Warren, the CRUCIBLE ramps and the lineage view were built this session.

What breaks this now

  1. Speed. Python is fine for tools and load-time generation, and too slow for per-frame crowds. Fix: cache by (type hash, seed); P1 Rust core.
  2. WFC at larger sizes with 3×3 patterns. Fix: backtracking, or grow in 24px chunks with edge constraints (P2).
  3. Parity covers the runtime only. The workbench's converter and UI-kit preview are separate JS code with no gate. Fix: move them behind the same parity gate, or label them preview-only (they are, today).
  4. extends replaces lists. The aquatic goblin lost its tunic because parts replaced the parent's. Fix: add a parts_add key that appends.
  5. The flash check is an approximation. Fix: it is labelled UNVERIFIED; run a certified tool (such as PEAT) before shipping public animations.
  6. Nobody but me has used it. SPIRE's own known limit applies: every fixture is synthetic. Fix: your first real Book of Cities catalog import will find what I couldn't.

Nearly free improvements

  • Name seeds: --seed-name Grubnak hashes a name to a seed, so an NPC's name is its look.
  • GIF export of idle animations (stdlib LZW, about 60 lines).
  • pixelgoblin watch for Dropzone: frog.png plus frog.tag in a folder converts on arrival.
  • Register the 27 SLM-e pieces into slme.db: one command, since the manifests already validate.
  • Squint: a readability check at 1x (silhouette contrast against a background).

What I think

The core bet held up. One small integer engine, many doors, and a determinism contract that now holds across two languages. That is rarer than it sounds, and it is the part no existing editor has. The workbench is useful but thin. That is the right order, not a flaw. The most valuable thing this session produced might not be PixelGoblin at all: it is the Vanilla Core fix, because every future composite run in your stack would have hit it.
